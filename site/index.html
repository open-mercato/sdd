Spec-driven development

Specify it.

Skills

Nine skills. One job each.

What the agent does inside each skill, in order. One entry point, then one skill per step.

om-sddSets up the repository, starts a change and says what runs next.
  1. Vendors the state script and the conventions into the repository
  2. Creates the change folder and its state file
  3. Reads the state and names the next skill, or what blocks it
  4. Hands the approval commands to a human and never approves itself

Leaves .ai/sdd/ · change.json

om-sdd-discoverTurns a request into a one-page brief for one initiative.
  1. Reads the request, linked issues and the affected code before asking anything
  2. Asks only the two or three questions that could change scope
  3. Writes one page: outcome, problem, scope, rules and slices
  4. Tags every claim as evidence or as an assumption
  5. With existing requirements: indexes the document instead of interviewing, lists what it leaves unanswered, and pins its version
  6. Gets a skeptical read from a fresh-context agent, then confirms scope with the owner

Leaves brief.md

om-sdd-specWrites one spec that contains its own implementation plan.
  1. Loads the brief, the code and the capability specs the change touches
  2. Writes a skeleton with open questions and stops for answers
  3. Describes behavior as numbered acceptance criteria
  4. Plans phases and steps, each naming its criteria and its test
  5. Has a fresh-context agent review it, then waits for human approval

Leaves spec.md

om-sdd-mockupBuilds a high-fidelity mockup from the real design system and collects comments.
  1. Finds the app’s real components, tokens and closest existing screens
  2. Builds every screen and state as a dev-only route with fixture data
  3. Tags elements so each maps to a screen, a name and a criterion
  4. Adds the review overlay: press C, click any element, comment
  5. Fixes cosmetic comments and sends anything that changes behavior back to the spec

Leaves mockup/ · feedback.md

om-sdd-secureThreat-models the change and turns every mitigation into a required test.
  1. Reads the approved spec, the living threat model and how the code authenticates, scopes and validates today
  2. Describes the attack surface the change adds: entry points, data, trust boundaries
  3. Finds threats twice: STRIDE per element, then an abuse case per acceptance criterion
  4. Decides each threat: mitigate with a named control, or accept, which only a human can approve
  5. Writes a security criterion for every mitigation, in the same form as acceptance criteria
  6. Has a fresh-context agent attack the design, then records the result

Leaves security.md

om-sdd-validateChecks readiness before any code is written.
  1. Runs the deterministic traceability check
  2. Looks up every module, route and entity the spec names in the real code
  3. Checks backward compatibility and the repository’s own rules
  4. Confirms that the mockup and the spec agree, and that every security control exists or is planned
  5. Returns go, conditional or no-go with evidence, and changes nothing

Leaves validation.md

om-sdd-implementImplements the approved spec step by step on a resumable pull request.
  1. Works on its own branch and opens a draft pull request after the first commit
  2. Takes one plan step at a time and records each with its commit, so an interrupted run resumes
  3. Pins current behavior with a test before changing it, and writes a test for every acceptance and security criterion
  4. Builds UI from the approved mockup, with the same components
  5. Runs the full validation gate; the script refuses “done” without a green run for the current code
  6. Stops and reports when the code cannot match the spec

Leaves Pull request

om-sdd-verifyReviews and tests the pull request against the spec and the mockup, with evidence per criterion.
  1. Reviews from a context that did not write the code, and never fixes it
  2. Starts from deterministic diff signals: removed exports, destructive migrations, code without tests, silenced checks
  3. Runs the validation gate itself instead of trusting reported results
  4. Walks every UI criterion in a real browser and compares each screen with the approved mockup
  5. Builds the evidence table: every acceptance and security criterion needs a test or a screenshot
  6. Returns pass or fail by rule: any blocker, or any unwaived major, fails

Leaves verify.md

om-sdd-archiveFolds the change into the living description of the system.
  1. Applies added, changed and removed requirements to the capability specs
  2. Folds new threats, controls and accepted risks into the living threat model
  3. Does it on the pull request branch, so the description becomes true at merge
  4. Removes mockup routes and fixtures from application code
  5. Closes the change and leaves the merge to a human

Leaves capabilities/*.md

Why it works

Less rework. More confidence.

Three rules keep the process small.

One spec, one plan

Requirements, architecture and tasks live in a single document. No competing planning docs.

Mockup before code

A high-fidelity mockup replaces the separate UX design phase and becomes an acceptance artifact.

Evidence, not promises

Review and QA check the result against what the team actually agreed to build.

FAQ

Questions, answered.

Is the implementation plan a separate phase?

No. om-sdd-spec writes it together with the specification.

Do I need a UX design phase?

No. The mockup is built after the spec, from your application’s real components.

What if the mockup changes the requirements?

Cosmetic comments are fixed in the mockup. Anything that changes behavior goes back to the spec, which is then approved again.

I already have requirements. Do I still run Discover?

Yes, but it takes minutes. Discover indexes your document instead of interviewing, flags what it leaves open, and pins its version so a later change is noticed.

Is the Secure step a penetration test?

No. It is design-level threat modeling that produces required tests. It does not replace a penetration test for high-risk changes.

Is it available today?

The om-sdd skills are in preview and are not yet part of the public skills repository.
